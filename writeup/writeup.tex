\section{MLIR: An Introduction}
\subsection{LLVM MLIR IR objects}
This section briefly looks at what MLIR IR objects look like, and why they are
important. In LLVM, MLIR is an intermediate representation between high-level
source code and LLVMIR:

\noindent Source Code (Python, C, C++, etc.) $\to$ MLIR $\to$ LLVMIR $\to$ machine code

\noindent Some variants/dialects of MLIR:

\begin{enumerate}
	\item arith
	\item func
	\item linalg
\end{enumerate}

\noindent An example in arith:
\begin{verbatim}
module {
  func.func @add_example(%a: i32, %b: i32) -> i32 {
    %0 = arith.addi %a, %b : i32
    return %0 : i32
  }
}
\end{verbatim}

\noindent These representations allow for machine-agnostic standardized analyses and optimization passes.

\subsection{Core Concepts}
\begin{itemize}
	\item \textbf{Operations}: The basic unit of computation in MLIR. Each
	      operation represents a single step and can produce results and take
	      inputs.

	\item \textbf{Regions}: Containers attached to operations. Regions hold blocks
	      and allow for things like control flow constructs and
	      function bodies.

	\item \textbf{Blocks}: Ordered sequences of operations.
	      Blocks may take arguments, similar to function parameters.

	\item \textbf{Dialects}: Namespaces that group related operations and types.
	      They allow MLIR to support multiple domains Ex: \texttt{arith},
	      \texttt{func}, \texttt{llvm}.
\end{itemize}

\subsection{Why MLIR?}
\begin{itemize}
	\item \textbf{Multi-level abstraction}: MLIR allows different levels of
	      lowering, allowing us to reason on different levels of representations.
	      (tensor, cf are examples)

	\item \textbf{Extensibility via dialects}: New domains can define custom
	      operations and types without modifying the core system.

	\item \textbf{Reusable infrastructure}: Optimization passes, analyses, and
	      transformations can be shared across different dialects and stages.
\end{itemize}

\section{Why Use Haskell to Parse Python}

\subsection{Motivation}

This project uses Haskell to parse Python because Haskell gives a direct way to
represent syntax in the type system. For example, expressions, statements, and
functions can be represented as explicit data types instead of being handled as
generic objects or loosely structured values.

Haskell is also a good fit for parsing because parser operations can be
composed from smaller pieces. This makes it easier to build the parser step by
step and to keep failure cases visible through types such as \texttt{Either}
and \texttt{Maybe}. These features make the parsing and lowering code easier to
organize for this project.

In C++, the same structures can be represented more strictly, but doing so
often requires more boilerplate around classes, pointers, references,
ownership, and error handling. For this project, Haskell provided a simpler way
to describe the language structure without adding those cumbersome extra
implementation details. I personally parsed a smaller language using C++ and
found it very cumbersome compared to Haskell.
\subsection{Parsing Strategy}
My strategy here was to leverage the library \texttt{language-python}, which
parses Python, and convert it into an AST defined by \texttt{language-python}
itself.

Next, I wrote a converter to take the `language-python` AST and create my own
AST with all the operations I chose to support in Python, a much smaller subset
of Python. (for simplicity)

The file which corresponds to this can be found under pmm/ConvertAST.hs. The
AST which I convert to is pmm/AST.hs.

\subsection{Mapping to MLIR}
Lastly, my plan was to take this AST and lower it to MLIR. I was planning to
leverage the library \texttt{mlir-hs} to do so.

I didn't fully succeed here.

What success would've looked like here is:

\begin{enumerate}
	\item Lower \texttt{Python--} AST to an AST that \texttt{mlir-hs} explicitly defined
	      in its codebase by completing the file LowerMLIR.hs
	\item Leverage the builder inside the project to automatically emit MLIR code.
\end{enumerate}

I stopped short at creating the MLIR AST converter partway.

The file which corresponds to this is found under pmm/LowerMLIR.hs.

\section{System Architecture}
\subsection{Pipeline Overview}
Python source $\rightarrow$ Haskell AST $\rightarrow$ MLIR AST $\rightarrow$
MLIR lowering.

\subsection{PythonMLIR-- Language Subset}

This project uses a smaller subset of Python called \texttt{PythonMLIR--}. The
planning file \texttt{docs/planning/PythonMLIR--.md} describes which Python
features are supported and which features are excluded.

The file \texttt{docs/planning/pythonmlir\_supported\_ops.py} gives concrete
examples of the supported syntax and operations. These files define the input
language used by the parser, AST conversion step, and MLIR lowering step.

Limiting the subset of Python which I would be compiling was necessary to keep
my project appropriately scoped. It avoids many dynamic Python features and
focuses on typed variables, integer operations, expressions, and basic control
flow.

\subsection{Example}
\begin{lstlisting}[language=Python]
x: int = 5
y: int = 10
z: int = x + y
\end{lstlisting}

\begin{lstlisting}

# Example MLIR (simplified)

%0 = arith.constant 5 : i32
%1 = arith.constant 10 : i32
%2 = arith.addi %0, %1 : i32
\end{lstlisting}

\section{Reproducibility}
The repository for this project is available at:

\begin{verbatim}
https://github.com/handel-fan/efp_final
\end{verbatim}

To run this project, the repository should contain the following libraries and
project directories:

\begin{itemize}
	\item \texttt{language-python}: Used to parse Python source code into a Haskell
	      AST. This is required by \texttt{pmm.cabal}.
	\item \texttt{mlir-hs}: Used for the planned MLIR AST construction and MLIR
	      emission.
\end{itemize}

The main project is located in \texttt{pmm/}. The Haskell source files are:

\begin{itemize}
	\item \texttt{pmm/Main.hs}
	\item \texttt{pmm/ConvertAST.hs}
	\item \texttt{pmm/PMMAST.hs}
	\item \texttt{pmm/LowerMLIR.hs} INCOMPLETE
\end{itemize}
The external library directories should be placed at the repository root, at the
same level as \texttt{pmm/}. In this layout, \texttt{language-python} and
\texttt{mlir-hs} would both be sibling directories of \texttt{pmm/}.

The file \texttt{pmm/Main.hs} is the entry point for the executable. It reads a
Python file path from the command line, reads that file, and sends the file
contents through the parsing pipeline. First, it uses \texttt{language-python}
to parse the source program into the host Python AST. If parsing succeeds, it
then calls \texttt{ConvertAST.convertModule} to convert that host AST into the
project's smaller \texttt{PythonMinusMinus} AST. The resulting project AST is
printed as output. Unfortunately the output is not pretty. The MLIR lowering
step is left as the next planned step in the pipeline.

Example input programs are located in \texttt{pmm/examples/}. The main example
used for testing is:

\begin{verbatim}
pmm/examples/int_declarations.py
\end{verbatim}

The project can be built from the \texttt{pmm/} directory using:

\begin{verbatim}
./build_pmm.bash
\end{verbatim}

It can be run using:

\begin{verbatim}
./run_pmm.bash
\end{verbatim}

The executable defined by the Cabal file is \texttt{run-pmm}. The Cabal file
requires \texttt{language-python == 0.6.0}. The \texttt{mlir-hs} library should
also be present in the repository because \texttt{LowerMLIR.hs} was intended to
lower the project AST into MLIR structures.

\section{Results}
\subsection{What Works}
The working parts of the project are:

\begin{itemize}
	\item A defined subset of Python in \texttt{docs/planning/PythonMLIR--.md}.
	\item Concrete examples of supported syntax in
	      \texttt{docs/planning/pythonmlir\_supported\_ops.py}.
	\item A conversion step from the \texttt{language-python} AST to my own smaller
	      project AST.
	\item A project AST defined around the Python features I chose to support.
	\item A partial lowering path from my project AST toward MLIR structures.
\end{itemize}

\subsection{What I learned}
Some of the things I learned in this project are:

\begin{itemize}
	\item How to convert and walk ASTs using Haskell. In this regard, I learned a lot
	      about how the host AST defines a lot of what you have to account for when
	      converting to your own AST. Furthermore, I learned about structural and
	      recursive traversal of the AST. Here is an example which I saw repeatedly:
	      \[
		      \text{Module}
		      \rightarrow
		      \text{Statement}
		      \rightarrow
		      \text{FunctionDef}
		      \rightarrow
		      \text{Arguments}
		      \rightarrow
		      \text{Body}
		      \rightarrow
		      \text{Expression}
		      \rightarrow
		      \text{Literal}
	      \]

	\item Deep dives on Haskell language constructs - monads, record syntax,

	\item MLIR structure and operations: Operations, Regions, Blocks, Control Flow, and
	      how if, for, function calls, etc. all actually work under the hood.

	\item Terminators, block args, and other MLIR structural details.

	\item How much more difficult a project is than it seems.
\end{itemize}
